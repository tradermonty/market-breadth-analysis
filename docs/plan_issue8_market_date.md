## Contract

1. Use the offline XNYS schedule from `exchange-calendars>=4.5,<5` for real sessions and UTC close instants (including DST, holidays and early closes). Default clock is aware UTC; injected naive datetimes are rejected, rather than interpreted in machine-local time. Calendar lookup uses a bounded recent window (45 days), and reports library version/name. This is a maintained calendar snapshot, not a real-time exchange status service.
2. Resolve the latest scheduled completed session (`close <= now`) and expected delivered session (`close + configurable delivery grace <= now`, default 30 minutes). Grace affects expected freshness only: if today's completed close is already supplied, include it immediately even inside grace. During grace, yesterday's available close can be eligible. Filter observations against actual sessions and completed close instants; never transform a weekend/future/non-session observation into a fabricated trading-day observation.
3. API lookup uses only the existing FMP wrapper's SPY daily-price method, with a 14-day bounded date request. Parse explicit daily dates and finite positive closing prices, select the maximum valid observed completed session independent of row order. Invalid/malformed payload or no qualifying observations yields an explicit low-confidence fallback, never a verified available date. A valid earlier observation during provider delay remains selected; metadata marks whether it meets expected freshness.
4. Saved-data date resolution reads only `data/sp500_price_data.csv` using the existing loader, with no FMP call. Require a valid date index and a single numeric price column; choose its latest valid completed-session observation. Missing/corrupt cache falls back with low confidence. This does not implement strict offline acquisition throughout analysis/backtests (Issue #14).
5. Preserve existing `get_last_trading_day()` behavior (previous weekday, not an exchange calendar). Preserve `get_latest_market_date()` as a string-returning compatibility wrapper with a structured resolver underneath. Add `resolve_default_end_date(use_saved_data, now=None)` for the original proposal's public helper, and a structured variant used by `main()`.
6. Structured result records selected date, latest completed date, expected delivered date, source, confidence, reason code, generation UTC time, calendar/version and `publication_eligible`. Actual observation and freshness are distinct: a verified but stale provider/cache date is not publication-eligible. If observation lookup fails, use the calendar candidate with confidence `calendar_only`; if calendar fails/out-of-range, use an explicitly unverified previous-weekday estimate (before 16:00 New York excludes today), never label it exchange-verified.
7. `main()` writes `reports/market_date_resolution.json` before analysis for downstream #9 validation. Default API/cache runs with unverified fallback exit nonzero before fetching constituents or plotting. Verified but stale observations remain usable for research and have `publication_eligible=false` (the deployment gate belongs to #9). Explicit `--end_date` is validated as an ISO date and remains authoritative, without default-date API/cache lookup or silent clamping; its metadata is explicit/unverified and makes no publication eligibility claim. Reject end<start rather than silently replace it. CLI help/docs state these distinctions. Add `--data-arrival-grace-minutes` with finite, nonnegative values.
8. All exception metadata/logs use reason codes or shared redaction; no credentials in fallback diagnostics. No real API/workflow calls, live orders, deploys or merges in this task.
